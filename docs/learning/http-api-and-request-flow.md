# HTTP 接口与请求链路学习记录

## 1. 为什么值得学习这部分

运维和 SRE 经常要从入口开始排查问题：客户端发了什么请求、请求到了哪个服务、服务如何校验、在哪一层失败、最终返回什么状态码。

理解 HTTP 接口和服务请求链路，可以帮助我们：

- 阅读 API 文档并复现问题；
- 区分客户端参数错误、业务冲突和服务故障；
- 判断健康检查实际覆盖了什么；
- 理解监控指标、日志和告警应该在哪个环节采集；
- 在面试中讲清一次请求如何经过服务。

## 2. 一个 HTTP 请求由什么组成

以资源预约请求为例：

```http
POST /api/v1/activities/activity-001/reservations HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json
Idempotency-Key: demo-001

{"user_id":"user-001"}
```

请求主要包含：

- **方法**：`POST`，表达这次请求要执行的操作类型；
- **路径**：`/api/v1/activities/activity-001/reservations`，定位 API 资源和操作；
- **请求头**：描述请求元信息或控制信息，例如内容类型、幂等键；
- **请求体**：本次操作提交的数据，这里是用户 ID。

HTTP 方法是客户端和服务端共同遵守的语义约定；真正的业务行为由服务端路由函数实现。

## 3. GET、POST 和路径

### GET

`GET /api/v1/activities/activity-001` 用于读取活动信息。GET 按约定不应改变服务端业务状态，适合查询活动状态、名额和时间。

### POST

`POST /api/v1/activities/activity-001/reservations` 用于提交预约，会改变服务端状态，因此使用 POST。

### 路径层级

```text
/api/v1/activities/{activity_id}/reservations
```

- `/api`：项目约定的 API 路径前缀；
- `/v1`：接口版本，未来接口不兼容时可并存不同版本；
- `/activities`：活动资源集合；
- `{activity_id}`：路径参数，调用时由具体 ID 替换；
- `/reservations`：该活动下的预约操作资源。

路径命名是 API 设计约定，不是框架自动推断的业务含义。

## 4. 路径参数、请求头和请求体

| 输入位置 | 本项目字段 | 用途 | 当前校验/处理 |
|---|---|---|---|
| 路径参数 | `activity_id` | 指明要查询或预约哪个活动 | 在内存活动集合中查找，不存在返回 404 |
| 请求头 | `Idempotency-Key` | 标识一次逻辑操作，支持安全重试 | 必填，长度 1 到 128 |
| 请求体 | `user_id` | 标识预约用户 | 必填，长度 1 到 64 |

幂等键解决的是网络重试歧义：客户端可能没收到响应，但服务端已经完成操作。客户端用相同键重试时，服务返回首次成功结果，避免重复占用名额。

## 5. 响应状态码

| 状态码 | 本项目场景 | 解释 |
|---:|---|---|
| 200 | 活动查询成功、健康检查成功 | 请求成功并返回数据 |
| 201 | 预约成功 | 新预约已创建 |
| 404 | 活动 ID 不存在 | 目标资源不存在 |
| 409 | 已预约、名额已满、幂等键冲突、活动未开始/已结束 | 请求格式正确，但与当前业务状态冲突 |
| 422 | 缺少幂等键、用户 ID 为空或超长 | 请求没有通过参数校验，业务函数通常尚未执行 |
| 500 | 未处理的服务端异常 | 服务内部故障，需要结合日志和指标排查 |

## 6. 当前代码的对应位置

- FastAPI 应用创建：`app/main.py` 中 `app = FastAPI(...)`；
- 活动模型、名额和时间状态：`Activity`；
- 请求体验证：`ReservationRequest`；
- 健康检查路由：`GET /healthz`；
- 活动查询路由：`GET /api/v1/activities/{activity_id}`；
- 预约路由和幂等处理：`POST /api/v1/activities/{activity_id}/reservations`；
- 自动化行为验证：`tests/test_health.py`。

FastAPI 在启动时收集路由定义并生成 OpenAPI 描述；`/docs` 页面读取该描述，显示参数、请求体、响应码并生成可交互的调试界面。因此它展示的是已注册的 HTTP API，不是运维控制台。

## 7. 服务内部请求链路

```text
浏览器或调用方
  -> HTTP 请求
  -> Uvicorn 接收网络连接并解析 HTTP
  -> FastAPI 按方法和路径匹配路由
  -> Pydantic 校验请求数据
  -> 路由函数执行业务逻辑
  -> 当前进程内存中的活动/预约/幂等数据
  -> FastAPI 序列化响应
  -> Uvicorn 返回 HTTP 响应
```

- **Uvicorn**：ASGI 应用服务器，监听端口并处理网络连接；
- **FastAPI**：Web 框架，负责路由、依赖注入、请求/响应处理和 OpenAPI 文档；
- **Pydantic**：根据模型定义验证和解析输入数据；
- **路由函数**：实现本项目的健康检查、活动查询和预约规则；
- **内存状态**：当前临时存储，服务重启后丢失，不支持多副本共享。

## 8. 健康检查的边界

`GET /healthz` 返回 `{"status":"ok"}`，目前只证明应用进程可以接收并响应 HTTP 请求。

它不检查数据库、Redis、磁盘或业务依赖，因为这些组件目前尚未接入。后续需要区分：

- **存活检查（liveness）**：进程是否卡死到需要重启；
- **就绪检查（readiness）**：实例是否已准备好接收业务流量；
- **依赖巡检**：数据库、缓存、配置、资源和指标是否存在风险。

这几类检查不能混为一谈。依赖短暂故障不一定意味着应该重启整个服务。

## 9. 当前实现与生产系统的差距

- 状态存在进程内存，重启后清空；
- `Lock` 只在同一个 Python 进程中协调线程；
- 没有数据库事务、跨副本唯一约束或持久化幂等记录；
- 没有结构化业务日志、请求指标和追踪；
- `/healthz` 不是完整的依赖健康检查。

这些限制是当前原型的已知边界，后续通过数据库、容器和可观测性阶段逐步验证和替换。

## 11. 面试讲解练习

可以用自己的话说明：

> 一次预约请求先由 Uvicorn 接收，再由 FastAPI 根据 HTTP 方法和路径匹配路由；Pydantic 校验请求体，路由函数使用活动 ID、用户 ID 和幂等键执行预约规则，最后 FastAPI 将结果序列化为 JSON。当前数据保存在单进程内存，因此只适合本地验证；多副本一致性需要数据库事务和唯一约束。

这段描述应基于实际代码理解，不要把尚未实现的数据库、监控或生产能力说成已完成。
