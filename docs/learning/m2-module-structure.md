# M2 模块化结构学习记录

## 这一步解决什么问题

M1 为了快速验证业务，把模型、内存状态和所有 HTTP 路由放在 `app/main.py`。这种写法适合原型，但随着数据库、日志、指标和巡检加入，单文件会难以定位问题，也不利于多人协作。

本次只做结构整理，不改变接口和业务规则。目标是让每个模块有一个清晰职责，并用测试证明行为保持一致。

## 当前模块职责

```text
app/main.py
  └─ 创建 FastAPI 应用，挂载路由

app/models.py
  └─ Activity、ReservationRequest 等数据模型

app/store.py
  └─ 当前的内存数据、幂等记录、锁和重置逻辑

app/routes/health.py
  └─ GET /healthz

app/routes/activities.py
  └─ 活动查询和资源预约接口
```

## 一次请求如何流转

1. Uvicorn 接收 HTTP 请求并交给 FastAPI。
2. `main.py` 组装的应用根据路径找到对应路由模块。
3. FastAPI 使用 `ReservationRequest` 校验请求体。
4. `activities.py` 调用 `store.py` 读取或更新状态。
5. 路由函数返回字典，FastAPI 将它序列化为 JSON。

`main.py` 不应该重新实现预约规则；它只负责组装。这样后续替换数据库时，主要修改存储边界，不必把数据库代码混入应用入口。

## 为什么暂时保留内存存储

当前阶段的重点是验证模块边界和 API 行为。内存实现启动成本低、测试稳定，但不具备生产可靠性：服务重启会丢数据，多副本之间也不共享状态。后续接入 MySQL 时，数据库事务和唯一约束会替代这里的进程内字典与 `Lock`。

## 验收证据

- `python -m pytest`：13 项测试通过。
- 接口路径、状态码、幂等行为、重复预约、名额耗尽和并发防超卖行为与 M1 保持一致。
- `app.main` 继续导出核心对象，是为了避免学习阶段的测试和脚本因结构整理失效；这不是新的业务耦合。
