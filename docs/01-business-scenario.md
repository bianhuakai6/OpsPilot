# M1 业务场景：在线资源预约服务

## 1. 场景定位

这是一个被 OpsPilot 管理的示例在线服务。它模拟在线资源预约，不追求完整业务产品，目的是提供真实的请求流量、数据约束和故障场景。

## 2. 参与者

- **用户**：查询活动并提交预约。
- **平台运维人员**：发布版本、观察指标、执行巡检和处理故障。
- **OpsPilot**：管理服务生命周期，不直接替代业务逻辑。

## 3. 核心流程

```text
用户查询活动
  -> 服务返回活动状态和剩余名额
  -> 用户提交预约
  -> 服务校验活动状态和请求幂等键
  -> 服务写入预约记录并扣减名额
  -> 返回预约成功或明确失败原因
```

## 4. 第一版业务规则

1. 活动有开始时间、结束时间和总名额。
2. 未开始或已结束的活动不能预约。
3. 同一用户对同一活动只能成功预约一次。
4. 名额为零时，后续请求必须返回明确的“名额已满”。
5. 重复请求不能产生重复预约记录。
6. 业务错误和系统错误必须区分，便于指标和告警统计。

## 5. 第一版不做

- 用户注册和复杂鉴权；
- 支付；
- 多活动管理后台；
- 消息队列异步化；
- 复杂前端页面。

## 6. 运维价值

该场景提供后续实验所需的压力点：

- 活动开始时的突发流量；
- 并发请求下的名额竞争；
- 重复请求和幂等；
- 数据库或缓存依赖故障；
- 版本发布和回滚；
- 业务错误率、延迟和剩余名额观测。

## 7. M1 验收问题

- 一次预约请求经过哪些校验？
- 为什么重复请求必须具备幂等性？
- 并发扣减名额可能造成什么问题？
- 业务失败和系统失败如何区分？
- 哪些指标可以证明活动服务正在异常？
