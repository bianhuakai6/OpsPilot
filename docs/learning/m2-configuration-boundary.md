# M2 配置边界学习记录

## 为什么要集中管理配置

端口、运行环境、应用版本和数据库地址都可能随环境变化。如果把它们直接写在路由或业务函数中，开发、测试和生产之间切换时容易修改代码，增加误配置风险。

当前使用 `app/config.py` 定义 `Settings`，并从环境变量读取值。代码默认值服务于本地开发，部署环境可以通过环境变量覆盖，不需要修改业务代码。

## 当前配置项

| 环境变量 | 默认值 | 用途 |
|---|---|---|
| `OPSPILOT_APP_NAME` | `OpsPilot` | API 文档中的应用名称 |
| `OPSPILOT_APP_VERSION` | `0.1.0` | API 版本展示 |
| `OPSPILOT_ENV` | `local` | 当前运行环境标识 |
| `OPSPILOT_HOST` | `127.0.0.1` | 预留的监听地址配置 |
| `OPSPILOT_PORT` | `8000` | 预留的监听端口配置 |

当前启动脚本仍通过 Uvicorn 参数传入 host 和 port。这样做是有意的：`Settings` 先建立应用配置边界，下一步再统一启动入口，避免一次改动同时影响太多层。

## 请求处理中的位置

```text
环境变量
  -> Settings.from_env()
  -> FastAPI 应用元信息
  -> Uvicorn 启动参数
  -> 服务运行
```

配置读取不是业务逻辑。业务代码只使用已经解析好的配置对象，不应该到处直接调用 `os.getenv`。

## 当前边界和后续工作

- 当前只接入应用元信息和本地运行参数；
- 数据库和 Redis 尚未连接，不能把它们写成已完成能力；
- 下一步会在 Docker 可用后增加数据库连接配置和启动检查；
- 生产环境还需要区分非敏感配置与 Secret，密码不能提交到 Git。

## 验收证据

`tests/test_config.py` 验证默认值、环境变量覆盖和非法端口处理。配置变更后仍需运行完整测试，并启动服务检查 `/docs` 和 `/healthz`。
