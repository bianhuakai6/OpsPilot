# M1 内存版预约服务学习记录

## 为什么先用内存

M1 的目标是验证 HTTP 接口、业务状态、错误分类和幂等规则。使用内存集合可以减少外部依赖，让每条规则都能通过测试直接观察。

## 请求路径

预约请求依次经过：

1. FastAPI 解析路径和 JSON；
2. Pydantic 校验 `user_id`；
3. 根据活动 ID 查询内存活动；
4. 判断活动是否处于 `active`；
5. 判断用户是否已存在；
6. 判断剩余名额；
7. 写入用户集合并返回成功。

## 当前实现的限制

内存集合只适合单进程教学和规则验证：

- 进程重启后数据丢失；
- 多进程实例之间没有共享状态；
- 名额检查和写入还没有数据库事务或分布式并发控制；
- `reset_state()` 只用于测试和重复实验。

因此，当前代码不能宣称支持生产级并发报名。M2 引入关系数据库后，需要用唯一约束和事务重新验证幂等与名额一致性。

## 关键测试

- 正常预约会减少剩余名额；
- 同一用户重复预约返回 `already_registered`；
- 名额耗尽返回 `capacity_exhausted`；
- 不存在的活动返回 `activity_not_found`；
- 空用户 ID 在进入业务逻辑前被请求模型拒绝。

## 面试表达

我先用内存实现隔离业务规则和 HTTP 行为，避免过早引入数据库。实现中明确记录了进程重启、多实例和并发一致性限制，下一阶段使用数据库唯一约束和事务重新验证这些生产问题。
