# M4：SLO 与错误预算基线

## 1. 这一步解决什么问题

仅有“接口能访问”和“容器 healthy”还不能说明服务可靠。SRE 需要把可靠性目标写成可计算的 SLO，并观察实际请求是否消耗了允许的错误预算。

OpsPilot 现在提供只读接口：

```text
GET /api/v1/slo
```

它读取进程累计的 HTTP Prometheus 指标，只统计用户业务接口 `/api/v1/activities/...`，返回总请求数、5xx 数量、可用性、错误率、错误预算消耗和近似 P95 延迟。健康检查、巡检、SLO 查询和静态页面请求不计入业务 SLO。

## 2. 当前基线

默认目标来自 `app/slo.py`，容器部署也支持通过仓库根目录 `.env` 中的 `OPSPILOT_SLO_AVAILABILITY` 和 `OPSPILOT_SLO_P95_MS` 覆盖：

- 可用性：`99.9%`；
- P95 延迟：`500 ms`；
- 错误预算：`0.1%`，即每 1,000 次请求最多允许约 1 次 5xx。

可用性只把 5xx 视为服务错误，4xx 通常代表调用方输入错误，不直接消耗服务端可用性预算。可用性目标必须在 0% 到 100% 之间（不含 100%），P95 目标必须大于 0。当前统计窗口是进程生命周期，重启服务后会清零；这不是生产级长期 SLO 存储。

## 3. 如何解释结果

`status=pass` 表示当前累计快照同时满足可用性和 P95 目标；`fail` 表示至少一个目标超限；`no_data` 表示缺少请求或延迟样本，不能据此宣布服务可靠。

错误预算消耗率的计算是：

```text
错误预算消耗率 = 实际错误率 / (100% - 可用性目标) × 100%
```

例如目标为 99.9%，1,000 次请求出现 1 次 5xx，错误率为 0.1%，预算消耗 100%；出现 3 次 5xx，预算消耗 300%，说明预算已经超支。

## 4. 局限与后续

当前接口是本地进程累计快照，不替代 Prometheus 的按时间窗口查询、Grafana 看板和告警规则；P95 使用 Histogram bucket 做近似计算。首次演练曾发现健康探针流量会污染业务 SLO，现已限定统计到预约业务接口。后续 M4 会增加故障注入、恢复证据和事故复盘，把 SLO 从“静态目标”变成可验证的可靠性闭环。

## 5. 故障演练发现：依赖探测必须有超时

停止 Redis 的演练发现，若 Redis 客户端没有连接和读写超时，`PING` 可能长时间等待，健康检查也无法及时告诉调用方依赖已失效。停止 MySQL 的演练也暴露了 SQLAlchemy 连接缺少明确超时的问题。现在 Redis 和 MySQL 都使用 2 秒级连接/读写超时；依赖检查应在有限时间内失败，让 `/readyz` 返回 503，巡检则记录对应依赖失败，而不是让请求无限挂起。
