# M4：SLO 与错误预算基线

## 1. 这一步解决什么问题

仅有“接口能访问”和“容器 healthy”还不能说明服务可靠。SRE 需要把可靠性目标写成可计算的 SLO，并观察实际请求是否消耗了允许的错误预算。

OpsPilot 现在提供只读接口：

```text
GET /api/v1/slo
```

它读取进程累计的 HTTP Prometheus 指标，返回总请求数、5xx 数量、可用性、错误率、错误预算消耗和近似 P95 延迟。

## 2. 当前基线

默认目标来自 `app/slo.py`：

- 可用性：`99.9%`；
- P95 延迟：`500 ms`；
- 错误预算：`0.1%`，即每 1,000 次请求最多允许约 1 次 5xx。

可用性只把 5xx 视为服务错误，4xx 通常代表调用方输入错误，不直接消耗服务端可用性预算。当前统计窗口是进程生命周期，重启服务后会清零；这不是生产级长期 SLO 存储。

## 3. 如何解释结果

`status=pass` 表示当前累计快照同时满足可用性和 P95 目标；`fail` 表示至少一个目标超限；`no_data` 表示还没有完成请求，不能据此宣布服务可靠。

错误预算消耗率的计算是：

```text
错误预算消耗率 = 实际错误率 / (100% - 可用性目标) × 100%
```

例如目标为 99.9%，1,000 次请求出现 1 次 5xx，错误率为 0.1%，预算消耗 100%；出现 3 次 5xx，预算消耗 300%，说明预算已经超支。

## 4. 局限与后续

当前接口是本地进程累计快照，不替代 Prometheus 的按时间窗口查询、Grafana 看板和告警规则；P95 使用 Histogram bucket 做近似计算。后续 M4 会增加故障注入、恢复证据和事故复盘，把 SLO 从“静态目标”变成可验证的可靠性闭环。
