# M1 内存版预约服务学习记录

## 为什么先用内存

M1 的目标是验证 HTTP 接口、业务状态、错误分类和幂等规则。使用内存集合可以减少外部依赖，让每条规则都能通过测试直接观察。

## 请求路径

预约请求依次经过：

1. FastAPI 解析路径和 JSON；
2. Pydantic 校验 `user_id`；
3. 根据活动 ID 查询内存活动；
4. 判断活动是否处于 `active`；
5. 根据活动和幂等键检查是否是已成功请求的重试；
6. 判断用户是否已预约、活动是否有剩余名额；
7. 在单进程锁保护下写入预约和幂等结果，再返回成功。

## 幂等键和锁

客户端为一次逻辑请求生成 `Idempotency-Key`。网络超时后重试必须复用同一个键，这样服务才能区分“重放旧请求”和“用户发起的新请求”。

当前实现使用进程内字典保存结果，并用线程锁保护检查和写入的临界区。锁只能协调同一个 Python 进程中的线程，不能协调多个服务副本；服务重启后幂等记录也会丢失。

## 当前实现的限制

内存集合只适合单进程教学和规则验证：

- 进程重启后数据丢失；
- 多进程实例之间没有共享状态；
- 名额检查和写入还没有数据库事务或分布式并发控制；
- `reset_state()` 只用于测试和重复实验。

因此，当前代码不能宣称支持生产级并发预约。M2 引入关系数据库后，需要用唯一约束和事务重新验证幂等与名额一致性。

## 关键测试

- 正常预约会减少剩余名额；
- 同一用户使用新幂等键重复预约返回 `already_reserved`；
- 同一幂等键重放返回原成功结果且不重复扣减名额；
- 名额耗尽返回 `capacity_exhausted`；
- 并发请求不会超过内存活动名额；
- 不存在的活动返回 `activity_not_found`；
- 空用户 ID 在进入业务逻辑前被请求模型拒绝。

## 面试表达

我先用内存实现隔离业务规则和 HTTP 行为，并通过幂等键表达客户端重试语义。单进程锁只验证线程级的临界区保护，不代表多副本一致性；下一阶段要用数据库唯一约束和事务重新验证生产场景。
