# M2 本地 HTTP 压测基线

## 目的和边界

压测用来观察指定环境、接口和并发设置下的响应表现，帮助建立可重复比较的基线。它不是生产容量承诺，也不能只凭一次本地结果推断云上吞吐。当前工具仅发送 GET，不会创建预约或修改业务数据。

## 运行

服务启动后，在项目根目录执行：

```powershell
python scripts/load_test.py
```

默认对 `/healthz` 进行 15 秒、8 并发的请求。报告包含总请求数、成功/失败数、错误率、吞吐量、延迟 P50/P95/最大值和少量错误样例，默认保存在 `reports/generated/`。

也可以指定目标、时长、并发和报告路径：

```powershell
python scripts/load_test.py --url http://127.0.0.1:8000/api/v1/activities/activity-001 --duration 30 --workers 4 --output reports/generated/activity-read.json
```

P50 表示一半请求的延迟不高于此值；P95 表示 95% 请求不高于此值。失败请求包括非 2xx/3xx 响应和网络错误，脚本会返回状态码 `2`，便于自动化识别。

## 指标入门：并发、吞吐量和延迟

可以把一次 HTTP 请求想成一个顾客到窗口办理业务：

- **并发数（concurrency）**：同时有多少个顾客正在办理。当前工具里的 `workers` 就是并发工作线程数，例如 4 表示最多同时发出 4 个请求。它不是请求总数，也不是系统容量。
- **吞吐量（throughput）**：单位时间完成了多少个请求，通常写成 `req/s`。例如 2 秒完成 200 个请求，吞吐量约为 `200 / 2 = 100 req/s`。
- **延迟（latency）**：一个请求从发出到收到响应花了多久，页面以毫秒（ms）显示。延迟越低，单次请求越快。

并发和吞吐量不是一回事：并发表示“同时在处理多少个”，吞吐量表示“每秒完成多少个”。在其他条件相近时，提高并发可能提高吞吐量，但也可能让 CPU、连接池或数据库拥堵，导致延迟和失败率上升。

### P50 和 P95 怎么看

把所有请求的延迟从小到大排序：

```text
10, 11, 12, 13, 14, 15, 16, 80, 120, 300 ms
```

- **P50**（第 50 百分位）：约一半请求不超过这个时间，代表普通用户的典型体验。
- **P95**（第 95 百分位）：约 95% 请求不超过这个时间，剩下约 5% 是更慢的请求，能暴露尾部延迟。

因此不能只看平均值。平均值可能被少量慢请求掩盖，而 P95 能回答“绝大多数用户是否都能及时得到响应”。例如 P50=5ms、P95=200ms，说明多数请求很快，但仍有明显慢请求，需要继续查日志、线程池、数据库或依赖服务。

### 结合本项目页面理解

压力测试页固定使用只读目标，避免测试改变预约数据。开始任务后，后端用受限数量的 workers 重复发送 GET 请求，并记录每次请求的耗时和结果。页面每 500ms 查询一次任务快照，展示：

1. 请求总数和失败数：这次实验实际完成了多少请求。
2. 失败率：失败数除以总请求数，用来判断是否出现错误或超时。
3. 吞吐量：已完成请求数除以任务已运行时间。
4. P50/P95：从已完成请求的延迟样本计算出的典型延迟和尾部延迟。
5. 延迟曲线：观察运行过程中是否出现突然变慢或逐渐恶化。

一次本地实验只能说明“在当前电脑、当前版本、当前依赖状态下的表现”。要比较优化前后，必须尽量固定目标接口、持续时间、并发数、机器负载和数据库状态；不能把页面上的某个 `req/s` 直接当成生产容量承诺。

比较结果时应固定机器、应用版本、目标接口、时长、并发，以及 MySQL/Redis 等本地负载。该工具没有验证长时间稳定性、复杂用户行为、生产流量模型或独立压测机容量，不能把单个 RPS 数字当作系统容量结论。后续应结合应用指标、主机资源和数据库指标定位瓶颈。
